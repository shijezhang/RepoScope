## 1. 项目定位与最终交付

### 1.1 产品定位

面向需要理解陌生 Python 代码库、评审代码改动或选择回归测试的开发者，输入仓库与一组代码变更，输出可核查的影响分析和测试验证报告。

系统回答四个问题：

1. 改动了哪些函数、类、模块或配置？
2. 哪些调用方或业务入口可能受影响，依据是什么？
3. 应该运行哪些已有测试，为什么选择它们？
4. 哪些结论已经经过执行验证，哪些仍不确定？

核心交付物是“变更影响与回归验证报告”。自然语言交互服务于分析与补查，不作为产品的唯一入口。

### 1.2 最终交付的三个部分

| 用户要求 | 重构完成后的交付物 | 核心验收依据 |
|---|---|---|
| 能写进简历、具有区分度的高质量项目 | 可运行源码、可复现样例、评测集、实验结果、部署说明、简历描述 | 有业务任务、有独立设计、有强基线与消融实验；效果数字均能回溯到实验 |
| 清晰易懂、用于面试的技术报告 | 项目技术报告、关键决策记录、完整案例、面试问答、术语表 | 能从业务问题讲到实现、取舍、结果和局限；与最终代码一致 |
| 简洁美观的前端 | 可实际操作的 Web 工作台、加载与异常状态、证据浏览和报告导出 | 主流程清楚；可完成真实分析、查看证据、执行测试、理解结果 |

本计划仅定义上述交付要求。技术报告正文、前端实现和效果数据在后续开发中产生。

### 1.3 在简历中的角色

- Eval Harness 实习展示评测和问题定位；RepoScope 展示把知识、工具和执行结果组成一个业务系统的能力。
- SemiAgent 实习展示后训练数据建设；RepoScope 展示独立完成产品与工程交付的能力。
- MemoAgent 展示记忆和经验复用；RepoScope 聚焦代码结构、变更分析和回归验证，避免重复。
- 图学习研究作为结构建模的背景；项目价值通过任务结果验证，不把已有算法包装成原创研究。

专业性来自问题建模、可靠实现和证据，而非组件数量。只有被实验支持的能力进入简历主描述。

## 2. 范围与代表性任务

### 2.1 V1 支持范围

| 项目 | V1 约定 |
|---|---|
| 分析对象 | Python 源码、pytest 测试、Markdown 文档、与测试有关的少量配置文件 |
| 主要输入 | 已登记的本地 Git 仓库、base 与 head 两个可解析 commit；可附自然语言任务 |
| 比较语义 | 默认直接比较两个快照；PR 模式显式使用 merge-base 到 head，并显示实际比较的 SHA |
| 仓库规模 | 首轮目标为 2～3 个中小型公开 Python 仓库；规模与资源在 M0 实测后冻结 |
| 分析内容 | 符号定位、调用与导入关系、潜在影响范围、已有测试选择、测试执行与报告 |
| 运行形态 | 单机 Web 应用、CLI、一个持久化任务 worker；以个人演示和小团队试用为目标 |
| 代码保护 | 分析固定快照，测试在独立执行目录与容器中完成，不更改被分析仓库的原工作区 |
| 未提交改动 | 后续增强项：冻结工作区内容与 patch hash 后分析；V1 首先保证 commit 对比可复现 |

后端计划以 Python 3.12 为参考运行环境，首批目标代码语法限定在 Python 3.10～3.12；目标项目的测试解释器由各自执行配置确定。M0 核验依赖兼容性后锁定补丁版本。超过解析器支持范围的语法明确标记失败，不吞掉文件。

### 2.2 首版不承担的功能

- 自动修改代码、自动提交 PR、自动合并和自动部署。
- 多语言静态分析、完整 Python 类型推断、所有动态调用的精确解析。
- 对任意 GitHub URL 自动准备环境并执行代码的公共服务。
- 大规模多租户平台、分布式图数据库、复杂权限后台。
- 以社区摘要或整仓聊天为主的通用代码知识库。

这些范围限制用于保证核心任务做深。未来扩展应有用户需求或实验依据。

### 2.3 三个验收样例

以下为计划中的自建 fixture 场景，不是当前仓库已有功能或真实线上案例。

| 样例 | 输入 | 期望结果 |
|---|---|---|
| A：跨模块影响 | 修改金额计算函数的边界判断 | 找到调用链上的订单接口与相关测试；展示路径；测试验证边界行为 |
| B：删除与重命名 | 删除旧函数并调整部分调用方 | 保留 base 侧的旧符号证据；识别遗留引用；不因 head 找不到符号而漏报 |
| C：动态行为与不足证据 | 经插件注册或 getattr 调用目标函数 | 展示静态解析边界；使用已有覆盖或扩大测试范围；无法验证时保留未知结论 |

成功样例之外，最终演示必须至少包含一个失败或证据不足的样例。

## 3. 计划形成的三项核心亮点

### 3.1 亮点一：结构关系、变更信息与测试覆盖共同驱动影响分析

以程序解析获得代码关系，以版本差异定位变更，以测试覆盖补充运行证据。语义检索用于定位自然语言需求，图遍历用于追踪关系，测试执行用于验证行为。

需回答的面试问题：为什么文本检索不够？为什么图可达不等于实际受影响？静态与动态信息发生冲突时如何处理？

证据要求：对比强混合检索与无图方案，展示影响识别的准确率、召回率、失败类型和实际案例。

### 3.2 亮点二：根据证据缺口选择工具的有界 Agent

Agent 能发现“当前证据不足以解释影响”或“测试未覆盖关键路径”，再选择补充查询或测试动作。工具结果结构化保存，关键结论绑定证据，调用次数与执行时间有预算。

需回答的面试问题：哪些步骤需要模型决策？固定流水线是否已经足够？如何防止无限补查、重复运行和错误引用？

证据要求：与使用相同工具、相同预算的固定流程比较，验证动态补查是否提高任务完成率或减少不必要调用。

### 3.3 亮点三：快照一致的增量索引与可复现验证

按 Git 变更更新符号、关系和检索索引，同时处理删除、重命名、入边失效和跨文件重新解析。所有分析与证据绑定不可变快照。

需回答的面试问题：为什么只重解析变更文件不够？如何证明增量结果与全量构建一致？旧测试覆盖是否还能使用？

证据要求：在相同最终快照上对比全量和增量构建的规范化结果、时间及资源消耗。

### 3.4 区分度的判定

代码图、RRF、工具调用和 coverage 都不是本项目原创。个人贡献落在三个机制如何组合，以及如何解决以下具体问题：

- 从两个代码版本推导可解释的潜在影响，并正确处理不确定调用。
- 将影响范围变成有依据的测试计划，再使用执行反馈修正报告。
- 在索引、覆盖信息和分析报告之间维持版本一致性。

如果实验未证明其中某项有收益，保留真实结果并调整主卖点，不编造提升。

## 4. 总体架构与技术选择

### 4.1 数据流

~~~mermaid
flowchart TD
    A[仓库与 base/head] --> B[冻结两个代码快照]
    B --> C[AST 与符号解析]
    B --> D[Git 差异映射]
    C --> E[有向代码图与符号索引]
    C --> F[BM25 与向量索引]
    D --> G[变更符号与影响候选]
    E --> G
    H[版本绑定的测试目录与覆盖信息] --> I[测试候选与确定性排序]
    G --> I
    F --> J[Agent 查询与补查]
    G --> J
    I --> J
    J --> K[受控测试执行器]
    K --> L[执行结果与证据]
    L --> J
    J --> M[结构化报告与引用校验]
    M --> N[Web 工作台和报告导出]
~~~

离线索引、基线覆盖采集和在线分析分别计时。首次全量覆盖的成本不能隐藏在在线性能之外。

### 4.2 默认技术方案

| 层 | 默认选择 | 原因与边界 |
|---|---|---|
| 语法解析 | Python ast + 自建有限符号解析器 | 单语言下依赖简单，可获得源码范围；AST 不自动提供准确调用图 |
| 图模型 | NetworkX MultiDiGraph | 保留方向、关系类型及多个调用位置；规模达到瓶颈后再考虑独立图数据库 |
| 持久化 | SQLite 元数据、节点边与任务表；文件保存大产物 | 支持事务与单机部署；内存图是快照的运行视图 |
| 代码检索 | 标识符查找 + BM25 + Dense + RRF + Reranker | 为自然语言查询提供强基线；结构化 diff 无需强制先经过语义检索 |
| 模型接口 | 兼容 OpenAI 协议的 provider adapter | 继承现有接口思路；增加结构化输出、用量、超时与版本记录 |
| Agent | 显式状态机 + 结构化工具调用 | 便于追踪、恢复和控制；V1 不引入多 Agent |
| 测试 | pytest + coverage.py + pytest-cov | 采集已有测试与覆盖关系；保留 nodeid、阶段、快照和配置 |
| 执行隔离 | 预构建 Docker 镜像与仓库执行配置 | 运行目标项目测试需要隔离其代码和依赖 |
| 服务端 | FastAPI + 独立持久化 worker + SSE | REST 创建与查询任务，SSE 推送进度；API 进程不承担长测试 |
| 前端 | React + TypeScript + Vite；Tailwind CSS + Radix UI；React Flow 局部图 | 围绕报告组织界面，图用于解释路径 |
| 交付 | CLI + 本地 Web + Docker Compose 启动说明 | 先保证单机可复现，不把公网部署作为验收前提 |

M0 核验所选版本并产生锁文件。计划不预先声称当前环境已安装这些组件。

Embedding 首轮复用现有 bge-m3 候选，Reranker 选择一个可本地运行的 cross-encoder；模型具体 revision、许可证、内存和延迟在 M0 比较后冻结。若资源不足，调整模型并重新冻结基线，不能悄悄关闭 Dense 后仍宣称完成强基线比较。

### 4.3 核心数据契约

以下字段是设计契约，具体 Pydantic 模型在 M0/M1 实现。

| 对象 | 必需信息 |
|---|---|
| Repository | repo_id、规范化来源、允许分析的路径、执行配置标识 |
| Snapshot | snapshot_id、repo_id、commit_sha、tree_hash、源码清单 hash、解析器与配置版本、状态 |
| Symbol | symbol_id、snapshot_id、相对路径、模块名、限定名、种类、源码范围、签名和内容 hash |
| Relation | snapshot_id、source_id、target_id、relation_type、调用位置、解析方法、解析等级 |
| ChangeSet | base_snapshot_id、head_snapshot_id、比较模式、文件状态、旧/新行区间、patch_hash |
| TestCase | snapshot_id、pytest nodeid、测试文件、参数化信息、收集状态、历史耗时 |
| CoverageEvidence | 被测源码快照、测试套件 hash、nodeid/context、阶段、文件行集合、环境与 coverage 配置 hash |
| AnalysisRun | run_id、输入快照、状态、预算、工具调用记录、model/prompt/config 版本、起止时间 |
| Claim | claim_id、结论类型、相关符号、evidence_ids、verified/inferred/unknown 状态、限制 |
| TestExecution | execution_id、执行源码与测试版本、nodeids、镜像与命令配置 hash、退出码、逐测试结果、日志位置 |

标识约定：

- Symbol ID 包含快照、路径、限定名、种类及必要的同名定义区分信息。行号是定位信息，不作为跨版本身份的唯一依据。
- 跨快照使用显式 SymbolMapping；精确匹配优先，重命名或移动的内容相似性只作为候选证据。
- 证据引用始终包含 snapshot_id、路径、源码范围和内容 hash。报告可同时引用 base 与 head，但必须区分。
- unresolved 调用单独保存调用点与候选原因，不创建虚假的确定目标。
- 解析、图、BM25、Dense 和测试目录在完整构建成功后统一发布快照；失败快照不能成为默认查询版本。

### 4.4 服务接口草案

| 接口 | 作用 | 契约要求 |
|---|---|---|
| POST /api/repositories | 登记支持范围内的仓库 | 服务端校验仓库路径与配置；返回 repo_id |
| POST /api/repositories/{repo_id}/snapshots | 为指定 commit 创建索引任务 | 返回 job_id；构建完成后返回可查询 snapshot_id |
| POST /api/analyses | 创建分析 | 必须提供版本输入与比较模式；支持 Idempotency-Key |
| GET /api/analyses/{run_id} | 查询状态与报告 | 返回任务状态、完整度、快照与已持久化结果 |
| GET /api/analyses/{run_id}/events | SSE 进度 | 支持事件游标恢复；不通过字符串解析推测业务状态 |
| POST /api/analyses/{run_id}/test-runs | 执行报告中的测试计划 | 校验 plan_id、快照和 nodeid；返回 execution_id |
| POST /api/analyses/{run_id}/cancel | 取消任务 | 幂等；区分已收到取消与资源已回收 |
| GET /api/evidence/{evidence_id} | 查看证据 | 返回固定快照内容和可验证位置 |
| GET /api/analyses/{run_id}/export | 导出报告 | format 为 json、markdown 或 html；从同一报告模型生成 |

界面新增测试执行后，报告生成新的 revision，保留此前版本。追问产生关联的子分析记录或报告 revision，不覆盖原始证据。M0 固定具体选择，并使 UI、CLI 和评测采用同一契约。

统一错误响应包含 code、message、retryable 和关联任务 ID。至少区分 invalid_revision、unsupported_syntax、snapshot_not_ready、test_environment_unavailable、budget_exceeded；不可恢复错误不能无限重试。

## 5. 代码图与变更分析

### 5.1 节点与关系

节点：Module、Class、Function、Method、TestCase；文档使用独立 EvidenceDocument，避免混入可执行依赖关系。

| 边 | 方向 | 用途 |
|---|---|---|
| CONTAINS | 模块/类 → 成员 | 定位结构和源码归属 |
| IMPORTS | 导入方 → 模块或符号 | 跨模块依赖与重新解析 |
| CALLS | 调用方 → 被调用方 | 反向查找潜在调用者 |
| INHERITS | 子类 → 基类 | 识别继承相关影响；不直接等同方法实际调度 |
| COVERS | 测试 → 行范围/符号 | 带执行上下文的覆盖证据 |
| DOCUMENTS | 文档 → 符号 | 解释需求或接口约定，不自动传播代码影响 |

测试覆盖按行保存原始事实，符号级覆盖为派生视图。一个测试覆盖函数，不代表验证了所有分支或参数。

### 5.2 解析能力分层

M1 必须支持模块级函数、类与方法定义、普通/相对导入、导入别名、限定名、同模块直接调用和可确定模块目标的调用。

M2 扩展嵌套作用域、局部遮蔽、同名符号、简单继承与 self 调用。对于 self.method，只有能够证明目标唯一时标记 resolved；存在覆写或动态分派时保留多个候选或 unknown。

getattr、动态导入、monkey patch、复杂工厂返回、装饰器替换、运行时插件注册、反射与跨进程调用不保证精确解析。

解析等级为 resolved、candidate、unresolved，表示证据类型，不表示经过校准的概率。代码解析不导入目标模块，也不执行它。

### 5.3 从 diff 到变更符号

1. 从 Git 取得 NUL 分隔的文件状态，并读取零上下文差异；处理路径空格、增加、删除、重命名与空文件。
2. 分别将旧行区间映射到 base 符号，新行区间映射到 head 符号。
3. 函数体、签名、装饰器、类基类和模块级变量分别记录变更类型。
4. 无法归属函数的模块初始化或全局变量变更，使用模块级种子，保守扩大到导入方。
5. 删除符号从 base 图反向分析；新增符号从 head 图分析；修改符号同时保留两侧关系。
6. 配置、conftest、依赖锁文件等不适用普通 CALLS 分析，走专门的测试失效与回退规则。

Git 的重命名判定是启发式；没有识别到重命名时按删除加新增处理，优先保证不遗漏。

### 5.4 影响候选生成与排序

第一步由确定性规则生成候选：

- 变更符号自身。
- 沿 CALLS 入边追踪调用者，沿必要的 IMPORTS/INHERITS 关系补充模块与类型依赖。
- 使用 visited 集合处理递归与循环依赖；按边类型限制遍历，不把任意图边混在一起。
- 使用覆盖信息标注候选符号或行是否曾被测试执行，并关联相关测试。行覆盖本身不提供调用顺序，不能据此宣称观察到了整条运行调用链。

第二步排序：

- 直接变更、已解析调用链、覆盖证据、路径距离及语义相关性分别作为特征。
- 首版使用可解释规则排序，不训练一个缺少标注支撑的风险模型。
- 最大跳数、节点数和路径数由配置限制；达到上限时返回 truncated，不能显示“全部影响已分析”。
- 小图可穷尽支持关系；大图截断后扩大测试范围或把结论降为部分分析。

每条候选输出一条代表性证据路径及附加依据。LLM 可以解释和补查，不能凭语言生成不存在的关系。

报告区分“潜在结构影响”“曾有覆盖关联”“已观察到行为变化”。现有测试通过也不等于完全无风险。

## 6. 代码检索与测试选择

### 6.1 检索设计

代码以函数、方法、类和模块说明为主要检索单元。长函数切分时保留父符号和行区间，补充模块、签名、docstring 和必要的类上下文。

标识符分词同时保留完整名称与 snake_case/camelCase 子词。精确 symbol/path 查询优先走结构化索引；自然语言任务使用 BM25 与 Dense 召回、RRF 融合及 Reranker 重排。

图扩展与文本召回保留各自来源，融合后依据上下文预算去重。不能简单取前五个片段并按字符截断，导致关键签名或证据丢失。

代码搜索基线与业务流程分开：给定明确 diff 的分析无需增加一次无用模型路由；自然语言追问才需要语义定位。

### 6.2 测试目录与覆盖

在目标项目的固定执行环境中 collect pytest nodeid，处理参数化测试，不自行拼接不存在的测试标识。

基线覆盖采集使用 pytest-cov 的 test context 能力，保存原始覆盖数据，并在适配器中区分测试执行阶段。共享 fixture、模块导入和无测试归属的执行行单独处理，不能把它们错误归到最后一个测试。

覆盖绑定源码版本、测试套件、依赖环境、解释器与采集配置。任何关键条件不匹配时，标记 stale 或 unavailable。

base 覆盖用于对 head 做保守测试推荐，不能伪装成 head 的已验证覆盖。未变代码可经精确内容映射迁移覆盖线索，但保留其来源；修改符号的旧覆盖不证明新分支已覆盖。

### 6.3 选择策略

测试候选来源依次包括：

1. base 覆盖命中变更符号或行范围的测试。
2. 覆盖潜在受影响调用者的测试。
3. 静态依赖、测试文件命名、测试描述和语义检索得到的候选。
4. head 新增或修改的测试。
5. 无法可靠解析或覆盖不足时，回退到相关模块、包或全套测试。

选择器以“覆盖尽可能多的重要变更/影响候选，控制预计测试时间”为目标，采用确定性的加权覆盖贪心方案。权重与测试耗时只在开发集调节，并记录配置。

coverage 证据强于单纯命名相似；每条推荐标注来源。测试预算不足时显示未覆盖候选，不把预算内完成等同验证完成。

以下变更触发扩大范围：conftest/共享 fixture、pytest 配置、依赖锁文件、模块级副作用、解析失败、无法映射的删除和全局注册逻辑。首版允许这些任务退回全套测试，报告回退原因和比例。

### 6.4 测试结果解释

测试状态至少包括 passed、failed、error、skipped、xfail、xpass、timeout、cancelled、not_run。测试收集失败、环境失败与断言失败分开记录。

“确认回归”至少需要同一可比测试在 base 通过、head 失败，并排除已知环境问题和不稳定失败。base 也失败时标记既有失败；仅 head 可运行的新测试失败时，报告 head 验证失败，不伪造 base 对照。

相同 nodeid 不保证测试相同。对照还需核对测试内容、共享 fixture、配置和依赖环境；它们发生变化时优先使用两侧都兼容的冻结测试，无法做到则降低结论等级，并解释不具备严格对照的原因。

必要时执行有限次数的复跑检查波动性，次数和新增成本公开。无法确定时标记疑似回归。

## 7. Agent 决策、工具与报告

### 7.1 固定步骤与模型决策的边界

固定步骤负责冻结输入、解析 diff、生成影响候选、校验工具参数、执行测试和验证引用。这些步骤不交给模型自由发挥。

模型负责理解补充需求、识别待证实的假设、在允许工具中选择下一步、解释结果。初始影响集合和测试计划由确定性模块提供，模型不能无依据删除重要候选。

Agent 对每轮动作保存简短的决策摘要，例如“动态调用目标不确定，查询该调用点已有覆盖”。无需保存或展示模型内部思维链。

### 7.2 状态机

~~~mermaid
stateDiagram-v2
    [*] --> queued
    queued --> preparing
    preparing --> analyzing
    analyzing --> retrieving: 存在证据缺口
    retrieving --> analyzing
    analyzing --> testing: 有待执行的验证
    testing --> analyzing: 接收结果
    analyzing --> reporting: 证据足够或达到预算
    reporting --> completed
    preparing --> failed
    retrieving --> failed
    testing --> failed
    queued --> cancelled
    preparing --> cancelled
    analyzing --> cancelled
    retrieving --> cancelled
    testing --> cancelled
    reporting --> cancelled
~~~

任务完成状态与报告完整度分开：completed 可以对应 complete、partial 或 inconclusive。只要仍有未知路径、未执行测试或截断，就必须在报告中保留。

worker 意外退出的运行进入 interrupted 恢复流程：先核对已有工具与测试 execution_id，再决定续跑。恢复不能直接复制上一轮的测试调用。

### 7.3 工具契约

| 工具 | 输入 | 输出与限制 |
|---|---|---|
| find_symbol | snapshot_id、名称或路径 | 精确/候选符号，含解析信息 |
| search_code | snapshot_id、query、filters、limit | 片段、排序来源和证据 ID |
| get_neighbors | snapshot_id、symbol_id、relation_types、direction、limit | 带类型与来源的局部关系 |
| find_paths | snapshot_id、起终符号、允许边、预算 | 有限路径、是否截断 |
| read_evidence | evidence_id | 固定版本源码与行号，不读取任意系统路径 |
| get_test_candidates | changeset_id、scope、budget | 已收集 nodeid、推荐理由、预计耗时和未覆盖项 |
| run_tests | analysis_id、执行配置 ID、收集到的 nodeids、预算 | execution_id、结构化结果、日志证据 |
| get_test_result | execution_id | 已存在结果或运行状态 |

工具调用参数经 schema 与快照归属校验；模型不能传任意 shell 命令。相同快照、环境和测试集合的重复请求先查已存在的执行状态。显式复跑产生新 attempt，并注明原因。

初始预算建议：最多 6 轮模型决策、12 次工具调用、2 批测试、测试总时长 120 秒、任务总时长 180 秒。模型累计输入/输出预算也显式配置。以上是开发起点，M0/M4 根据样例实测调整后冻结，首次索引与覆盖采集独立计时。

停止条件：

- 关键影响结论已有证据，选定验证完成，无进一步可执行的关键补查。
- 预算耗尽、连续重复查询无新增证据或工具不可用：生成部分报告。
- 用户取消：停止新工具提交，并终止或回收正在执行的测试任务。

### 7.4 报告结构

1. 分析对象：仓库、base/head、比较模式、分析时间。
2. 结论概览：变更内容、潜在影响、测试结果、主要未验证项。
3. 影响条目：相关符号、变更类型、代表性依赖路径、来源版本。
4. 测试计划与结果：选择理由、实际运行状态、对照条件与执行成本。
5. 证据：源码片段、差异、覆盖记录和测试日志。
6. 限制：动态调用、解析失败、覆盖过期、图截断、未执行测试。
7. 运行元数据：配置、模型、索引版本和工具记录，默认折叠。

结构化 JSON 为唯一事实来源，Web、Markdown 和 HTML 导出从同一份数据渲染。

引用校验分两层：

- 确定性检查：ID 存在、属于该运行允许快照、行号和内容 hash 匹配；路径每条边存在。
- 语义检查：抽样人工核查结论是否被证据支持。ID 正确不能自动证明解释正确。

引用检查失败时降级或移除无依据结论，同时报告缺口。摘要生成失败仍可交付确定性的影响和测试表格。

## 8. 增量更新与版本一致性

### 8.1 为什么不能只重解析修改文件

被修改文件可能改变导出符号、类继承或函数签名，导致其他文件原有引用需要重新解析。删除文件也会留下旧入边；旧测试覆盖还可能失效。

增量方案必须同时更新文件自身产物与依赖这些产物的解析结果。

### 8.2 更新流程

1. 使用上一已发布快照与新 Git tree 计算差异。
2. 复制或复用未变文件的不可变解析产物；新快照仍有独立身份。
3. 移除变更/删除文件的旧符号与其贡献的关系、文本和向量索引条目。
4. 解析新增与修改文件，建立新的导出符号表。
5. 根据反向导入索引与调用点引用索引，重新解析可能受导出变化影响的其他文件。
6. 传播到受影响的符号解析依赖稳定；无法界定失效范围时回退全量构建。
7. 重建或更新检索索引；M1 先全量建立 FAISS 派生产物，M5 再实现稳定 ID 的删除与更新。
8. 校验悬空边、符号引用、索引数量及文件 hash；将覆盖标记为有效线索、过期或需重采集。
9. 所有产物完成后事务性发布，新查询才使用新快照；旧任务仍引用旧快照。

复用缓存的键包含文件内容、解析器/规则版本、模块解析配置和必要依赖指纹。仅按文件内容缓存跨模块符号解析是不充分的。

### 8.3 验收方式

对相同 head 分别执行全量构建和 base→head 增量构建：

- 比较规范化符号、关系、证据引用与检索条目 ID；排序后计算语义 hash，排除时间戳和内部序号。
- 使用固定查询检查召回条目及分数容差。向量与重排组件须固定模型和设置。
- 针对新增、删除、重命名、跨模块导出变化、循环导入、配置变化及失败恢复分别验证。
- 记录耗时、重新解析文件比例、峰值内存和回退全量比例。

首个可用版本允许检索索引全量重建，但只能称为“解析增量化”；全部相关阶段有实测证据后才宣称“端到端增量索引”。

## 9. 评测方案与简历证据

### 9.1 首批仓库

候选为 [Click](https://github.com/pallets/click)、[HTTPX](https://github.com/encode/httpx)，以及本地自建小型订单服务 fixture。公开仓库用于验证真实代码结构，fixture 用于控制故障与边界条件。

候选仓库尚未在本项目中完成环境与样本可行性验证。M0 固定具体 commit、测试命令、依赖锁定方式和镜像，并检查：

- 能在支持的资源条件下稳定收集和运行目标测试。
- 能找到跨文件调用、配置变化和测试选择的代表性任务。
- 测试不依赖不可用的外部服务，或可明确划分稳定测试子集。
- 基线测试结果可重现；选用子集时所有方案使用相同候选池，并在结果中标明。

若其中一个仓库不满足要求，按相同标准替换。最终面试版本至少包含两个真实公开仓库，不能只展示自建示例。

### 9.2 任务集构成

首个正式任务集目标为 120 条，采用下列分层。数量是建设目标，不能用重复变体或低质量自动题目凑数。

| 任务类型 | 总数目标 | 开发集 | 保留测试集 | 主要验证 |
|---|---:|---:|---:|---|
| 变更影响与证据定位 | 40 | 10 | 30 | 影响候选、路径、引用及遗漏 |
| 测试选择与回归检出 | 40 | 10 | 30 | 相关测试、实际失败和成本 |
| 索引更新一致性 | 20 | 5 | 15 | 增删改、重命名、版本切换 |
| 边界与失败处理 | 20 | 5 | 15 | 动态调用、缺覆盖、预算耗尽和工具失败 |
| 合计 | 120 | 30 | 90 | 分类报告，不能混成单一“准确率” |

真实历史改动、人工构造变更和变异注入任务分开标记。回归任务以可控变异和可重放历史回归为主；正常 PR 通常不是带缺陷版本，不能直接当回归真值。

按仓库中的 PR/变更来源及其衍生变异分组切分；同源 patch 及近重复问题不能横跨开发集和测试集。另报告跨仓库验证结果；样本不足时明确不给出泛化结论。

先完成 12 条试验任务验证管线，再扩展至 30 条开发集。规则冻结后运行保留测试集，不能边看测试集结果边调整权重。

### 9.3 标注与真值来源

每条 case 至少保存：case_id、repo/commit、变更来源、输入描述、预期影响范围及其定义、证据位置、可运行测试、基线结果、人工判定理由、数据分组和标注状态。

影响任务的真值是“按明确标注规则确认应检查的符号/模块集合”，不是整个真实世界中的完整行为影响。标注同时保存未知项；不确定项不强行算负例。

标注流程：

1. 查看源码、相关契约与测试，独立于 RepoScope 输出建立候选真值。
2. 使用实际执行或人工代码追踪补充依据；记录标注所用证据。
3. 对至少 20% 样例争取第二位开发者复核；无法获得复核时明确标为单人标注，并记录自查程序与局限。
4. 记录争议和裁决，不将模型自动生成的答案直接作为金标准。

回归真值定义：

- 使用同一组适用于两侧的测试，在 base 通过、故障 head 失败，才能纳入“可检出回归”分母。
- 对新增测试单独建立兼容性判定；不能运行在 base 的测试不计入严格 base/head 对照。
- flaky、环境失败、无测试能杀死的变异分别计数，不并入确定性断言回归。
- 完整测试套件或冻结的稳定子集用于离线建立失败集合，不在在线测试选择之前暴露结果。

防止信息泄漏：在线选择器只能使用当时可得的 base 覆盖、head 代码、测试目录和声明允许的文档。不能提前读取 head 全套测试失败清单、隐藏真值、修复后的未来提交或测试集标注。

### 9.4 基线与消融

| 编号 | 方案 | 检验的问题 |
|---|---|---|
| B0 | 路径/标识符文本搜索与简单测试命名规则 | 最低成本基线能做到什么 |
| B1 | BM25 + Dense + RRF + Reranker，固定生成流程 | 强文本检索是否已足够 |
| B2 | B1 + 代码图影响分析，固定流程，无覆盖 | 图结构贡献多少 |
| B3 | B2 + 版本绑定覆盖与确定性测试选择，固定流程 | 覆盖和选择策略贡献多少 |
| B4 | B3 + 有界 Agent 动态补查与执行反馈 | 模型决策是否有额外收益 |
| T-all | 全部可运行测试 | 回归检出上限参照与执行成本参照 |
| T-cov | 仅按 base 覆盖选择测试 | 图扩展是否优于简单覆盖选择 |

B1～B4 使用同一模型、源码快照、上下文上限和工具/测试预算；固定流程可使用与 Agent 相同的工具。报告实际消耗，不能只保证上限相同。

补充消融：关闭证据检查、关闭覆盖、关闭动态图补查、不同图遍历预算、不同覆盖回退策略。每项消融对应一个设计问题，不为增加表格而堆实验。

图增益优先看 B2 对 B1；Agent 增益看 B4 对 B3；增量收益看相同 head 的全量与增量构建。

### 9.5 指标定义

设任务 i 的已标注影响集合为 G_i，系统候选为 P_i，在线选择测试为 S_i，离线确认 head 回归失败测试集合为 F_i，可运行测试池为 T_i。

| 指标 | 定义与解释 |
|---|---|
| 影响 Precision / Recall / F1 | 以 P_i 与 G_i 交集计算；按任务宏平均，并报告模块级/符号级及任务类型 |
| 结构路径有效率 | 输出路径中边、方向、快照均有效的比例；不等同于业务结论正确率 |
| 结论证据支持率 | 人工复核中被证据充分支持的实质性结论比例；同时报告结论覆盖与遗漏 |
| 回归任务检出率 | 在 F_i 非空的任务中，S_i 与 F_i 有交集的任务比例 |
| 失败测试召回率 | 各任务中被选中的失败测试数量 / 全部已确认失败测试数量 |
| 测试数量缩减率 | 1 - 选中测试数 / 同一可运行测试池数量 |
| 回归执行节省 | 1 - 选择测试的实测执行时长 / 同一环境全测试池执行时长 |
| 在线总时长 | 图查询、检索、模型与选中测试的总耗时，不能只统计测试部分 |
| 索引一致率 | 增量与全量规范化结果一致的任务比例 |
| 更新加速比 | 同一 head 全量构建时长 / 增量构建时长，同时记录变更比例 |
| 完整任务成功率 | 按分类 rubric 判断必要结论、证据与执行均满足要求的任务比例 |
| 运行可靠性 | 工具错误、超时、重复测试执行、取消残留、快照错配分别计数 |

无影响真值的任务单独统计误报；没有回归的任务不进入回归检出率分母。无法判断与执行失败作为单独结果报告，不能自动按成功或普通错误处理。

成本记录至少包括 LLM 请求数、输入/输出 token、Embedding/Reranker 时间、峰值内存、索引大小与执行 CPU 时间。若折算金额，注明当时价格来源和日期。

### 9.6 实验条件与结果呈现

- 冻结硬件、解释器、依赖、模型 revision、prompt hash、随机种子、检索预算和数据库快照。
- 冷启动、热缓存、首次覆盖、后续单次分析分别报告；给出“首次使用总成本”和“稳定使用单次成本”。
- 有模型随机性的核心方案原则上做 3 次重复，预算不允许时披露次数；不要将重复运行视为独立任务扩大样本量。
- 按变更来源分组计算配对差异和 bootstrap 区间；小样本结果表述为观察，不宣称统计显著。
- 至少展示一个图无收益、一个 Agent 无收益或反而更慢的案例，说明适用边界。
- 结果保存在机器可读文件中，摘要表由脚本生成，不手工编辑分数。

### 9.7 验收目标与未达标处理

以下为计划目标，不是已有成绩，也不是面向任意 Python 仓库的承诺。

| 层次 | 目标 |
|---|---|
| 必须通过的正确性检查 | 声明支持的索引变更 fixture 中，全量/增量规范化结果一致；报告不存在跨快照错误引用；不存在无依据的“测试通过” |
| 产品可交付 | 两个真实仓库主流程可重放；失败与取消可处理；前端与导出一致；安装、模型与测试环境有清晰说明 |
| 重点争取的效果 | 图方案在多跳影响任务上相对 B1 的 Recall 提升至少 10 个百分点，同时宏平均 Precision 下降不超过 5 个百分点 |
| 测试选择目标 | 在可检出回归子集上保留至少 95% 的任务检出率，并争取测试执行中位耗时减少至少 30% |
| 增量目标 | 当变更 Python 文件比例不超过 5% 时，争取中位更新加速比至少 2，且一致性门槛通过 |
| Agent 保留标准 | 相对 B3 在复杂任务上呈现可解释的成功率收益，或以更低成本达到相当结果；不要求简单任务也调用 Agent |

业务指标只用于判断下一步设计。未达标时按错误类型调整，并使用新版本开发集实验；冻结测试结果如实保留。不能降低标注难度、剔除失败样例或反复调测试集来满足目标。

## 10. 运行可靠性与系统测试

### 10.1 长任务与恢复

- API 创建任务并返回 run_id；worker 从 SQLite 队列获取任务，持有租约并发送心跳。
- 单独保存分析状态和工具执行记录；每步完成后持久化，重启可恢复已完成结果。
- 测试提交前记录 execution_id；恢复时先检查对应容器/进程和结果，避免重复提交。
- SSE 事件包含单调 event_id，支持断线后从已知位置继续；浏览器刷新不会创建新任务。
- 取消传递到 worker 与测试容器；终止超时后回收资源，保留已有证据及 cancelled 状态。

### 10.2 目标仓库测试执行

每个登记仓库配一个执行 profile，包含镜像 digest、工作目录、收集命令、测试命令模板、环境变量白名单和资源限制。

依赖安装发生在环境准备阶段；正式测试默认不联网。测试容器不挂载宿主凭据、用户主目录或 Docker socket。执行源码复制到独立目录，允许项目测试写临时文件，但不写回用户原仓库。

应用的执行管理器负责创建和终止容器；模型只选择 profile 与 nodeid。操作系统进程隔离不能替代目标代码容器隔离。V1 以登记的公开样例和自有仓库为支持范围，不承诺抵御任意恶意仓库。

### 10.3 数据与资源

默认限制单文件大小、索引文件总数、单任务图规模、日志大小和并行测试数，避免一个任务占满资源。限制值在 M0 测量后写入配置并显示可理解的超限原因。

源码与报告按快照保存；用户删除快照前检查是否被运行引用。运行中或已固定用于演示/评测的产物不能被自动清理。

LLM 请求只包含本任务选中的代码证据，调用日志不保存密钥。仓库中的说明文档作为待分析内容，不获得修改执行配置或工具权限的能力。

### 10.4 与本项目改动相称的测试

| 层级 | 重点 |
|---|---|
| 单元 | 符号作用域、导入别名、diff 行映射、删除符号、循环图、测试选择与证据验证 |
| 属性/一致性 | 同一最终快照增量与全量等价；重复索引幂等；节点删除后不存在悬空关系 |
| 集成 | Git 快照→图与检索→分析→测试→报告，使用可控 fixture |
| 真实仓库契约 | 已固定仓库的测试收集、覆盖采集和指定 case 重放 |
| 故障注入 | worker 重启、模型超时、工具错误、测试超时、断线、取消和过期覆盖 |
| 前端 E2E | 创建分析、查看证据、执行/取消验证、恢复任务、导出报告 |

不为纯文案、颜色调整或简单配置搬迁增加复述实现的测试。每阶段完成必要检查后推进；仅在新失败或未解决疑点出现时扩展验证。

## 11. 前端产品与视觉方案

### 11.1 设计原则

用户应先看懂“改了什么、可能影响哪里、验证到哪一步”，再按需查看技术细节。首页不堆模型参数、节点数量或大幅装饰性图谱。

默认浅色、低饱和度配色，使用清晰的列表、表格和源码面板。主色建议为深蓝，辅助色用于状态；图和卡片只在帮助理解信息时出现。

V1 专注桌面分析体验，兼容较窄屏幕。深色模式属于后续增强，不影响首版验收。

### 11.2 页面与主要操作

| 页面 | 主要内容 | 主要操作 |
|---|---|---|
| 项目首页 | 仓库列表、最近分析、准备状态、示例任务 | 选择仓库、新建分析、查看历史 |
| 新建分析 | base/head、比较模式、变更摘要、可选问题、测试预算 | 确认分析输入并开始 |
| 分析工作台 | 结论概览、影响列表、证据详情、测试计划/结果、进度 | 查看路径、核对源码、运行建议测试、取消、追问 |
| 历史报告 | 固定快照的报告、执行记录、导出 | 重看证据、导出、以同一输入新建运行 |

M0 冻结的演示仓库以明确的“示例”入口展示。示例回放和实时分析使用不同标识；缓存报告不能伪装为正在实时运行。

### 11.4 关键交互

- 点击影响条目，同步定位源码差异与路径；切换 tab 不丢失当前条目。
- 路径默认展示一条最有解释力的链，按需展开邻居。超过节点上限时明确提示，避免全仓关系图形成视觉噪声。
- 静态关系、候选关系和覆盖证据使用文字标签及不同线型；颜色不是唯一辨识方式。
- 证据抽屉显示快照、路径、行号、源码及其支持的结论。点击旧版本证据必须打开 base 源码。
- 测试区域明确区分“建议运行”“运行中”“已通过”“失败”“未运行”，显示推荐理由和回退范围。
- 在线交互默认先出影响报告，再由用户执行所选测试；CLI/评测可显式启用自动验证模式，复用同一执行逻辑。
- 追问绑定当前分析与证据，不能偷偷切换到最新索引。需要新版本时创建新分析。
- SSE 断线后提示重连，刷新恢复已有 run_id；取消后保留已完成结果。

1. 1440×900 与 1280×800 下主流程布局完整；窄屏切为单列，主要操作可用。
2. 长路径、参数化测试名、较长代码行、零影响、无覆盖、上百条候选均有可用布局。

## 12. 未来技术报告与面试准备

### 12.1 报告定位

报告面向“懂 Python 和大模型基本概念，但未读过本项目代码”的读者。先讲一个业务问题，再沿一次真实分析解释模块。术语首次出现时用一句普通话解释。

报告以最终实现和实验为准，不复制计划中的目标为完成事实。每个机制说明：输入是什么、做了什么、输出是什么、为什么这样选、何时失效。

### 12.3 面试材料

最终另附面试准备文档，至少包含：

- 2 分钟介绍：业务问题、自己的三项设计、两项实测结果、一个限制。

8. 如何保证模型引用的代码和运行的代码是同一个版本？

10. 增量索引如何证明正确？什么时候回退全量？
11. 全套测试比系统分析还快时，产品是否值得使用？

## 13. 从当前 GraphRAG 迁移

### 13.1 当前事实与迁移原则

当前仓库已经具有文档处理、LLM client、NetworkX 图、BM25/Dense/RRF、固定检索生成、Gradio 界面和测试基础；它们可提供实现经验，但旧金融/论文数据不适合作为 RepoScope 业务评测。

本地现存 .claude 删除项及未跟踪 docs 属于开始本次规划前已有状态。本轮不处理它们；后续实施前重新检查差异，按明确范围提交，避免把不相关变更带入重构。

README 与旧技术报告的描述并非全部等同当前代码事实，迁移评估以实现和实际运行检查为准。

## 15. 关键风险与调整规则

| 实际问题 | 首选处理 | 不应采取的做法 |
|---|---|---|
| 动态调用解析不足 | 输出未知、使用覆盖补充、扩大验证范围 | 让 LLM 把猜测关系写成确定边 |
| 真实仓库测试环境难复现 | 固定稳定子集或按 M0 标准替换仓库 | 最终只演示自建玩具 fixture |
| 图比强检索基线无明显收益 | 按任务分层，检查标注与关系质量；对简单任务绕开图 | 隐藏负面结果或故意弱化基线 |
| Agent 比固定流程慢且无收益 | 保留固定主流程，Agent 仅用于疑难补查 | 强制每个任务调用多轮模型 |
| 无覆盖或过期覆盖太多 | 增加采集说明、回退策略和完整性标识 | 将推荐测试的执行成功当成覆盖充分 |
| 增量失效传播复杂 | 先做到解析增量，复杂变化回退全量 | 只刷新变更文件却宣称正确增量 |
| CPU 推理过慢 | 更换模型并重新冻结基线，或明确使用可获得的推理服务 | 删除强基线仍报告相同实验结论 |
| 全测试池很小 | 直接运行全套；把产品价值放在解释和影响定位 | 为证明缩减效果增加没有意义的测试 |
| 时间不足 | 优先保住两仓库、一个完整任务、关键实验、可用界面和报告 | 把重构压缩成换名与聊天界面 |

时间压缩顺序：先取消深色主题、复杂图操作、远端仓库自动导入、未提交改动、多语言和 API 外部集成；然后缩小语法支持和样本数量，并如实说明。核心证据、测试执行和版本一致性不能省略。
